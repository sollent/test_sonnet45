## ADR-001: Оптимистичные обновления UI

**Дата**: 01.11.2025  
**Статус**: ✅ Принято и реализовано

### Контекст
Пользователи жаловались на задержки при взаимодействии с задачами. При клике на чекбокс задача обновлялась только после ответа сервера (300-500ms), что создавало ощущение "тормозов".

### Решение
Реализовали оптимистичные обновления:
1. UI обновляется мгновенно при действии пользователя
2. Запрос на сервер отправляется в фоне
3. При ошибке UI откатывается к исходному состоянию

### Реализация
```typescript
// taskStore.ts
async toggleTaskCompletion(id: number): Promise<void> {
  const originalTask = { ...tasks.value[taskIndex] }
  
  // Оптимистичное обновление
  tasks.value[taskIndex] = optimisticTask
  
  try {
    const updatedTask = await taskService.toggleTask(id)
    tasks.value[taskIndex] = updatedTask
  } catch (err) {
    // Откат при ошибке
    tasks.value[taskIndex] = originalTask
    throw err
  }
}
```

### Последствия
**Плюсы:**
- Мгновенный отклик UI (0ms вместо 300-500ms)
- Лучший UX
- Приложение ощущается быстрее

**Минусы:**
- Сложнее логика (нужно управлять состоянием)
- Возможны edge cases при ошибках сети

### Альтернативы
1. **Ждать ответ сервера** - отвергнуто из-за плохого UX
2. **WebSockets для real-time** - избыточно для данного случая

## ADR-002: Неограниченная вложенность подзадач

**Дата**: 28.10.2025  
**Статус**: ✅ Принято и реализовано

### Контекст
Изначально планировалась только одноуровневая вложенность (задача → подзадачи). Но пользователи хотят разбивать сложные задачи на множество уровней.

### Решение
Реализовали self-referencing связь в Entity Task:
```php
#[ORM\ManyToOne(targetEntity: self::class, inversedBy: 'subtasks')]
private ?Task $parent = null;

#[ORM\OneToMany(targetEntity: self::class, mappedBy: 'parent', cascade: ['remove'])]
private Collection $subtasks;
```

### Последствия
**Плюсы:**
- Гибкость для пользователей
- Можно моделировать сложные проекты
- Естественная иерархия

**Минусы:**
- Сложнее UI (нужно рекурсивное отображение)
- Риск циклических ссылок (решено валидацией)
- Производительность при глубокой вложенности

### Решение проблем
1. **Циклические ссылки**: Валидация на backend запрещает установку задачи родителем самой себе
2. **Производительность**: Eager loading подзадач через Doctrine
3. **UI**: Компонент `TaskTreeModal` для визуализации дерева

## ADR-003: Точечное обновление вместо перезагрузки списков

**Дата**: 01.11.2025  
**Статус**: ✅ Принято и реализовано

### Контекст
После каждого изменения задачи (toggle, update, delete) весь список перезагружался через `fetchTasks()`. Это вызывало:
- Моргание UI
- Потерю позиции скролла
- Лишние запросы к серверу

### Решение
Вместо перезагрузки обновляем только конкретную задачу в массиве:

```typescript
function handleTaskCardUpdated(updatedTask: Task) {
  const taskIndex = tasks.value.findIndex(t => t.id === updatedTask.id)
  if (taskIndex !== -1) {
    tasks.value[taskIndex] = updatedTask
  }
}
```

### Последствия
**Плюсы:**
- Нет моргания UI
- Сохраняется позиция скролла
- Меньше нагрузка на сервер
- Быстрее работает

**Минусы:**
- Нужно следить за синхронизацией состояния
- Сложнее логика обновления

### Альтернативы
1. **Перезагружать список** - отвергнуто из-за плохого UX
2. **WebSockets** - избыточно для данного случая

## ADR-004: PrimeVue как UI библиотека

**Дата**: 20.10.2025  
**Статус**: ✅ Принято

### Контекст
Нужна была UI библиотека для Vue 3 с готовыми компонентами.

### Рассмотренные варианты
1. **PrimeVue** ✅
2. **Vuetify**
3. **Element Plus**
4. **Ant Design Vue**
5. **Кастомные компоненты**

### Решение
Выбрали PrimeVue

### Обоснование
**Плюсы PrimeVue:**
- Большой набор компонентов
- Хорошая документация
- TypeScript support
- Легкая кастомизация тем
- Accessibility из коробки
- Активная разработка

**Минусы:**
- Иногда избыточные стили (нужно переопределять)
- Не самая легкая библиотека

### Альтернативы
- **Vuetify**: Слишком Material Design, сложнее кастомизация
- **Element Plus**: Меньше компонентов
- **Кастомные**: Слишком много времени на разработку

## ADR-006: Docker для backend

**Дата**: 15.10.2025  
**Статус**: ✅ Принято

### Контекст
Нужна была изоляция окружения для backend разработки.

### Решение
Все backend команды выполняются внутри Docker контейнеров.

### Обоснование

- **Vagrant**: Слишком тяжеловесно

## ADR-007: JWT для аутентификации

**Дата**: 18.10.2025  
**Статус**: ✅ Принято

### Контекст
Нужна была система аутентификации для SPA.

### Решение
JWT (JSON Web Tokens) с refresh tokens.

### Обоснование
**Плюсы:**
- Stateless (не нужна сессия на сервере)
- Подходит для SPA
- Можно использовать для API
- Стандартный подход

**Минусы:**
- Нельзя инвалидировать токен (решено через refresh tokens)
- Нужно хранить токен на клиенте

### Реализация
- Access token: 1 час (короткоживущий)
- Refresh token: 7 дней (долгоживущий)
- Хранение: localStorage (планируется переход на httpOnly cookies)

### Альтернативы
- **Session-based**: Не подходит для SPA
- **OAuth только**: Избыточно для простого приложения

## ADR-008: TypeScript strict mode

**Дата**: 20.10.2025  
**Статус**: ✅ Принято

### Контекст
Нужно было решить, использовать ли TypeScript в strict mode.

### Решение
Используем TypeScript в strict mode.

### Обоснование
**Плюсы:**
- Меньше багов на production
- Лучший DX (автокомплит, подсказки)
- Самодокументирующийся код
- Легче рефакторинг

**Минусы:**
- Дольше разработка (нужно типизировать все)
- Сложнее для новичков

### Правила
- Типизировать **все**: props, emits, state, API responses
- Не использовать `any` (только `unknown` с type guards)
- Использовать interfaces для объектов
- Использовать enums для констант

## ADR-009: Композиция через Composables

**Дата**: 25.10.2025  
**Статус**: ✅ Принято

### Контекст
Логика завершения задач с подзадачами дублировалась в нескольких компонентах.

### Решение
Вынесли переиспользуемую логику в composable `useTaskCompletion`.

### Обоснование
**Плюсы:**
- DRY (Don't Repeat Yourself)
- Легче тестировать
- Переиспользуемость
- Композиция над наследованием

**Минусы:**
- Нужно продумывать API composable

### Пример
```typescript
// composables/useTaskCompletion.ts
export function useTaskCompletion() {
  const taskStore = useTaskStore()
  
  async function toggleTaskCompletion(task: Task) {
    // Логика завершения с подзадачами
  }
  
  return {
    toggleTaskCompletion
  }
}

// В компоненте
const { toggleTaskCompletion } = useTaskCompletion()
```

## ADR-010: Нормализация дат для API

**Дата**: 01.11.2025  
**Статус**: ✅ Принято

### Контекст
Даты постоянно сдвигались на день из-за timezone конвертации.

### Проблема
```typescript
// ❌ Плохо
date.toISOString().split('T')[0]
// "2025-10-31T21:00:00.000Z" → "2025-10-31" (но это 31 октября в UTC, а локально 1 ноября!)
```

### Решение
Создали функцию `formatDateForApi`:
```typescript
function formatDateForApi(date: Date): string {
  const year = date.getFullYear()
  const month = String(date.getMonth() + 1).padStart(2, '0')
  const day = String(date.getDate()).padStart(2, '0')
  return `${year}-${month}-${day}`
}
```

### Обоснование
- Игнорирует timezone
- Использует локальную дату пользователя
- Консистентно работает на frontend и backend

## ADR-011: Mobile-first подход

**Дата**: 20.10.2025  
**Статус**: ✅ Принято

### Контекст
Приложение должно отлично работать на мобильных устройствах.

### Решение
Разрабатываем сначала для мобильных, потом адаптируем для desktop.

### Обоснование
**Плюсы:**
- Проще адаптировать вверх (mobile → desktop) чем вниз
- Фокус на главном функционале
- Лучший UX на мобильных

### Правила
- Все компоненты должны работать на мобильных
- Большие кликабельные области (минимум 44x44px)
- Адаптивные шрифты и отступы
- Тестировать на реальных устройствах

### Breakpoints
```css
/* Mobile first */
.component { /* стили для mobile */ }

/* Tablet */
@media (min-width: 768px) { /* стили для tablet */ }

/* Desktop */
@media (min-width: 1024px) { /* стили для desktop */ }
```

## ADR-012: Умеренные border-radius

**Дата**: 01.11.2025  
**Статус**: ✅ Принято

### Контекст
Изначально использовались большие border-radius (16-24px), что выглядело слишком "игрушечно".

Уменьшили border-radius до умеренных значений:

## ADR-013: Единый focus style

**Дата**: 01.11.2025  
**Статус**: ✅ Принято

### Контекст
PrimeVue добавлял свои focus styles, что конфликтовало с кастомными стилями и создавало "двойные borders".

### Решение
Переопределили все focus styles в `main.css`:
```css
*:focus-visible {
  outline: none;
  box-shadow: 0 0 0 0.2rem var(--focus-ring-color);
}
```

### Обоснование
- Единообразный вид по всему приложению
- Accessibility (фокус все еще виден)
- Нет визуального шума
